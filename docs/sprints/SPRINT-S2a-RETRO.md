## 2. 잘된 점 (Keep)

**① 틀린 전제를 다시 확인한 것이 이 스프린트의 최대 성과다.**
계획은 I2a 의 선례를 따라 "Docker 금지 → 매퍼 SQL 은 XML 읽기로 검증(tier 3)" 을 그대로 적었다.
그 전제는 이미 틀렸다 — `embedded-postgres` 는 Docker 없이 실제 PostgreSQL 바이너리를 띄우고,
의존성은 이미 `pom.xml` 에 있었고, 톡전송 슬라이스가 이 환경에서 동작함을 증명해 두었다.
확인 한 번으로 이 슬라이스의 headline 결함이 <b>기술된 회귀에서 실행되는 회귀로</b> 바뀌었다.

> 톡전송 회고의 액션 A9 가 이 전제를 한 번 정정했는데, 그 정정이 <b>계획 문서에는 반영되지 않아</b>
> 다시 같은 문장을 쓰게 됐다. 정정은 회고가 아니라 계획에 반영되어야 한다 → §4 A3.

**② 결정을 시험이 아니라 구조로 강제한 두 곳.**
`BarredNumbers.MANDATORY` 는 설정 편집으로 119 를 등록 가능하게 만드는 일을 <b>표현 불가능</b>하게
했고(ADR 은 시험으로 보장하자고 했다), V3 §1 은 미해결 스파이크를 <b>DDL 적용의 전제 조건</b>으로
바꿨다. 둘 다 "나중에 잡는다" 를 "애초에 안 된다" 로 바꾼 사례다.

**③ 직전 스프린트의 발견을 리뷰 전에 미리 적용했다.**
I2a 의 SI2a-02 는 "API 계층 커버리지 0% — 서비스 시험이 마치 FR-AZ 를 덮는 것처럼 읽혔다" 였다.
이번에는 `SenderNumberWriteAuthorizationTest` 18 케이스를 <b>구현과 함께</b> 썼다. 회고 액션이
다음 스프린트에서 실제로 소비된 첫 사례다.

**④ 레거시 원본을 읽어 SQL 을 옮긴 것.**
`KKB_DPNO_HIS` 의 컬럼 구성을 추측하지 않고 `IDO.KKB_DPNO_HIS_C001` 을 읽었다. 컬럼 이름
(`ACN`, `REASON`, `RGSR_ID`, `RGSR_NM`)은 <b>추론이 아니라 인용</b>이며, 그 덕에 이력 테이블의
형태에 대한 가정이 코드에 들어가지 않았다.

## 3. 아쉬운 점 (Problem)

**① 성능이 두 스프린트 연속 최저 차원이며, 두 번 다 이유가 같다 — 측정을 시도하지 않았다.**
NFR-PERF-D02(P95 < 1s)와 NFR-PERF-D03(100건 삭제 < 5s)은 미측정이다. 100건 삭제는 한 트랜잭션 안의
100 × 3 문장이므로 "그럴듯하다" 고 말할 수 있지만, 그럴듯함은 측정이 아니다. I2a 도 같은 문장을
썼다(70점). 같은 자리에서 두 번 같은 점수를 받는 것은 우연이 아니다.

**② 시험이 <b>이름과 다른 이유로</b> 통과하고 있었다(SS2a-01).**
S1 의 `D-S8 — 눌리는 버튼을 두지 않는다` 는 기관을 고르지 않은 채 두 버튼이 비활성임을 단언했다.
S2a 에서 활성 조건이 붙자 그 시험은 <b>여전히 통과</b>했지만 더 이상 이름이 말하는 것을 시험하지
않았다. 우연한 통과는 작동을 멈춘 시험이며, 전체 스위트가 녹색이라는 사실이 그것을 가려 준다.

**③ 결정의 <b>비용</b>을 결정 시점에 찾지 못했다(SS2a-03).**
AMB-S09 결정 B(운영자 이메일 암호화)는 Skill 3 에서 내렸고, 그때는 `AOA_ADMIN` 의 화면 11 이
`RGSR_ID` 를 <b>표시</b>한다는 사실을 확인하지 않았다. 구현 중에 소비자 조사를 하다 발견했다.
ADR-SND-017 은 "테이블의 모든 독자를 알아야 한다" 는 규율을 세웠는데, <b>컬럼의 독자</b>에는
같은 규율을 적용하지 않았다.

**④ ADR 두 곳이 구현보다 약한 상태로 남았다.**
ADR-SND-021 은 "시험으로 보장" 이라 적혀 있는데 구현은 구조로 보장한다. ADR-SND-017/계획은
"컬럼 목록을 적는다" 였는데 구현은 `LIKE` 를 쓴다. 둘 다 구현이 더 낫지만, ADR 을 고치지 않으면
다음 읽는 사람은 ADR 을 믿는다.
