| Severity | Count |
|----------|-------|

Three risks (RISK-I01, I02, I03) are **not closable by writing code**. They need an operational audit, a cutover action, and a business decision respectively.

> **Revised 2026-08-20** — five risks added (RISK-I13…I17) by the screen-01 gap pass. Four of the five are consequences of decisions taken deliberately at that pass, which is why they are risks rather than defects: a rewritten requirement (I13), a strict validation ruling (I14), a single-display credential (I15), and two clocks for one edit (I16). The fifth (I17) is the coexistence window applied to the credential itself.

### RISK-I01 — Institutions already in the D-I1 state
- **영역**: 운영/보안 · **영향**: H · **확률**: M · **전략**: 완화
- **대응 계획**: The 중지 button has been writing `FT_INST_INFO` while every reader uses `FT_FTIS_INFO`. Operators who disabled an institution saw a success message and the institution kept its API access. **Fixing the code does not repair existing data.** Run an operational audit comparing institutions operators believe are stopped against `FT_FTIS_INFO.IS_STTS`, using the legacy audit log (`mntLogYn=Y` on `biztalk_admin_00_u001`) to identify past disable attempts
- **담당자**: PM · **모니터링**: **before Sprint I2 lifecycle work**; re-checked at cutover
- **비고**: Approved as an explicit action under AMB-I01. This is the most likely place in the whole programme where a *live* customer-facing problem already exists. Severity depends on how many institutions were disabled for cause (non-payment, abuse, contract end) rather than routine housekeeping

### RISK-I02 — Send-API enforcement gap during coexistence
- **영역**: 기술/보안 · **영향**: H · **확률**: H · **전략**: 수용 (bounded)
- **대응 계획**: FR-INSTL-009 requires a disabled or deleted institution to be refused by the send API, but enforcement lives in the legacy runtime (ADR-INST-016 §2.3). The portal writes the state and verifies it to its own boundary. **Named cutover action**: before the legacy send path is decommissioned, confirm it honours `IS_STTS` values other than `'Y'` — including `'D'`
- **담당자**: PM (cutover owner to be named) · **모니터링**: every sprint gate; mandatory at cutover
- **비고**: D-I1 is this exact failure mode already realised once. Declaring FR-INSTL-009 done on a green portal-side test would repeat it at the system level. Bounded only if cutover actually happens — **if cutover slips indefinitely, re-rate this as unbounded**

### RISK-I03 — Retained weak credentials
- **영역**: 보안 · **영향**: H · **확률**: M · **전략**: 수용
- **대응 계획**: AMB-I04 preserves existing `ATK` values so client integrations keep working. Those keys were generated by `Math.random()` in a browser and are stored plaintext. Exposure paths close (TM-I002/I003); entropy does not improve. FR-ATK-005 delivers rotation so a reissue campaign becomes scheduling rather than development
- **담당자**: PM + 정보보호 · **모니터링**: G3; revisit before internet exposure
- **비고**: RESIDUAL-I01 / TM-I005. **The two key populations are indistinguishable by query** — nothing in the stored value says whether it came from the browser or `SecureRandom`, so "how many weak keys remain" is unanswerable and any campaign must rotate all of them

### RISK-I04 — Dual writes from still-live legacy screens
- **영역**: 기술 · **영향**: M · **확률**: H · **전략**: 완화
- **대응 계획**: Legacy screens 00/01 remain operational during coexistence and edit the same rows, with no lock spanning both systems. Disable them at deployment (T-I2-12); until then rely on an optimistic `LAST_AMDT` check
- **담당자**: `architect` + 운영 · **모니터링**: deployment checklist
- **비고**: TM-I019. Low data-loss volume but high confusion potential — an operator editing in the legacy screen sees no sign the portal exists

### RISK-I05 — Delivered code queries a non-existent table
- **영역**: 기술 · **영향**: M · **확률**: H · **전략**: 회피
- **대응 계획**: `InstitutionMapper`, shipped in the 문자내역 slice, queries `BIZTALK_INSTITUTION` with columns `IS_CD`/`IS_NM`/`USE_YN`. **Every identifier is wrong** — the table is `FT_FTIS_INFO` with `FINTECH_ISCD`/`ISNM`/`IS_STTS`. Fixed as T-I1-01, the first task of Sprint I1
- **담당자**: `backend-developer` · **모니터링**: Sprint I1 day 1
- **비고**: The 문자내역 institution dropdown does not work outside tests. Its Javadoc flagged the guess honestly and asked for DBA confirmation — the process worked, but nothing forced the confirmation before merge. **Generalisable**: any mapper written from JS alone shares this exposure, because the legacy IDO's positional mapping hides the table's real column names

### RISK-I06 — `FT_FTIS_INFO` column semantics unconfirmed
- **영역**: 기술 · **영향**: M · **확률**: M · **전략**: 완화
- **대응 계획**: The table has 40+ columns; this slice writes 11 and must leave the rest untouched (ADR-INST-016 rule 4). `BSNN_STTS_CKYN` in particular gates `KKB_FT_FTIS_INFO_L003` and may be a **second, independent enable flag** whose relationship to `IS_STTS` is unrecoverable from code. DBA review required (AMB-I08)
- **담당자**: DBA + `data-model-designer` · **모니터링**: before Sprint I2 write path
- **비고**: A naive full-column write would null out 30 columns of operational configuration — `SRVR_IP`, `GRAMT`, `CHNL_DSNC` and others. C-03 tests for it, but the test only helps if the columns are known

### RISK-I07 — `IS_STTS='D'` is undocumented in the schema
- **영역**: 기술 · **영향**: M · **확률**: M · **전략**: 완화
- **대응 계획**: ADR-INST-014 overloads an existing column with a third value that no DDL comment declares. A future reader — or another team's query — may treat `'D'` as corrupt data or omit it from a filter. Mitigate with `InstitutionStatus` as the sole write path, a mapper-XML comment pointing to the ADR, and a note in the operations handover
- **담당자**: `architect` · **모니터링**: G2, handover
- **비고**: The accepted cost of avoiding DDL. The alternative — a correctly named column the legacy cannot see — trades a documentation problem for a correctness problem (ADR-INST-014 §3.1)

### RISK-I08 — Legacy cache staleness window unmeasured
- **영역**: 운영 · **영향**: M · **확률**: M · **전략**: 수용
- **대응 계획**: The portal triggers `FINInstitution` refresh and surfaces failures (unlike the legacy, which swallows them — D-I17). Coherence across multiple legacy instances cannot be guaranteed and the refresh cadence is unknown. Measure it in staging; document the observed window
- **담당자**: `architect` + 운영 · **모니터링**: staging validation
- **비고**: TM-I012. Compounds RISK-I02 — a disable may be correct in the database and stale in the cache that actually gates sending

### RISK-I09 — No legacy instance in staging
- **영역**: 외부 · **영향**: M · **확률**: M · **전략**: 완화
- **대응 계획**: TEST-PLAN §5 coexistence tests (C-01…C-05) need a legacy runtime alongside the portal. If staging has none, they degrade to schema-shape assertions. **That degradation must be stated in the sprint log**, not silently absorbed
- **담당자**: `qa-engineer` + 운영 · **모니터링**: Sprint I1 environment setup
- **비고**: Mirrors RISK-001 (no runnable legacy environment) from the proposal. The coexistence boundary is the one place where that gap has direct test consequences

### RISK-I10 — 기관코드 format authority unresolved
- **영역**: 기술 · **영향**: L · **확률**: M · **전략**: 완화
- **대응 계획**: The UI enforces exactly 6 characters with a `K0` prefix; the service contract declares length 16. 사업자등록번호 length is stated nowhere. Implement to the UI rule (AMB-I06 assumption A) and confirm with the domain owner before Sprint I2 validation work
- **담당자**: Domain owner · **모니터링**: before Sprint I2
- **비고**: Low impact because the rule is easy to change, but it must be settled **before** server-side validation ships — tightening a format rule after institutions exist is harder than choosing it correctly

### RISK-I11 — Excluded manager endpoints reappear
- **영역**: 보안 · **영향**: M · **확률**: L · **전략**: 회피
- **대응 계획**: 담당자관리 is out of scope (AMB-I02), but `biztalk_admin_00_l002` returns the full manager roster to any authenticated caller. A later "just port the remaining endpoints" sweep could reintroduce it. Guard with the absence test `managerEndpoints_doNotExist`
- **담당자**: `security-auditor` · **모니터링**: every sprint
- **비고**: Excluding a screen is not the same as excluding its endpoints. The absence test makes the exclusion enforceable rather than merely intended

### RISK-I12 — Audit retention term still unset
- **영역**: 규제 · **영향**: M · **확률**: M · **전략**: 완화
- **대응 계획**: OI-02 has been open since Skill 01. Institution lifecycle events and key reveals inherit ADR-006 retention, but the statutory term is unconfirmed. Under-retaining an institution-deletion record is a 전자금융감독규정 exposure
- **담당자**: PM + 정보보호 · **모니터링**: G3
- **비고**: Carried, not new. It now binds on more record types than before — key reveals and deletions are exactly the events an audit would ask for


### RISK-I13 — FR-INSTC-008 is now satisfied by less than it says
- **영역**: 기술/운영 · **영향**: M · **확률**: M · **전략**: 수용 (bounded)
- **대응 계획**: AMB-I11 rewrote the requirement: the portal invalidates its own view and does **not** refresh the legacy `FINInstitution` cache, because it cannot reach it. During coexistence a portal edit is therefore visible in the portal immediately and in the legacy runtime only after that cache expires or the instance restarts. Bounded by the same cutover action as RISK-I02 — disable legacy screens 00/01, then the legacy cache no longer serves an editing path
- **담당자**: PM (cutover owner) · **모니터링**: every sprint gate; mandatory at cutover
- **비고**: The mitigation is honesty, not a mechanism. The alternative — a notifier calling into IRIS_ADMIN — was declined as a call into a system this project does not own (ADR-INST-016). **If cutover slips indefinitely this stops being bounded**, exactly as noted on RISK-I02

### RISK-I14 — Strict 사업자등록번호 validation blocks unrelated edits
- **영역**: 운영 · **영향**: M · **확률**: M · **전략**: 수용
- **대응 계획**: AMB-I12 enforces FR-INSTC-009 on every save. A row holding a legacy value that is not 10 digits cannot be saved at all until that value is corrected — including when the operator only wanted to set 사용여부 to `N`. Mitigations: the error names the field, and 중지 has its own endpoint in I2b that does not run form validation, so the urgent case has a path that is not blocked
- **담당자**: PM · **모니터링**: first week of I2a in staging; revisit if it fires more than once
- **비고**: The escape hatch matters. Without the separate 중지 endpoint this ruling would mean bad reference data could delay stopping a customer, which inverts the intent. **Recorded so that the I2b lifecycle endpoints are not "simplified" into the form path later**

### RISK-I15 — A rotated key that never reaches the customer
- **영역**: 운영/보안 · **영향**: M · **확률**: M · **전략**: 완화
- **대응 계획**: FR-INSTC-011 commits rotation on confirmation and shows the new key **once**. If the operator loses it before distributing it, the customer's integration stays broken and the only recovery until FR-ATK-003 (reveal, I2b) exists is a second rotation. Mitigations: the confirmation names the consequence before committing; the key is displayed in a selectable field, not a transient toast; reveal lands in I2b
- **담당자**: `frontend-developer` + 운영 · **모니터링**: I2a acceptance; closed when FR-ATK-003 ships
- **비고**: The single-display rule is deliberate (FR-ATK-004 — the key is not stored anywhere client-side and not logged). The residual is operational, and it shrinks to nothing once reveal exists

### RISK-I16 — Two clocks describe one edit
- **영역**: 기술 · **영향**: L · **확률**: M · **전략**: 완화
- **대응 계획**: ADR-INST-017 writes `LAST_AMDT` on the database's wall clock while the audit record for the same edit is written on the application's UTC clock. An incident reviewer comparing the two sees a nine-hour gap that is correct but surprising. Mitigation: the offset is documented in the ADR §2.2, in `InstitutionAdminMapper`, and in the audit action's Javadoc
- **담당자**: `architect` · **모니터링**: G2; re-check if the deployment zone changes
- **비고**: The alternative — one clock for both — is worse in either direction: UTC in the column breaks comparability with legacy rows; wall clock in the audit store breaks ordering across instances

### RISK-I17 — The legacy popup still generates weak keys, into the same column
- **영역**: 보안 · **영향**: M · **확률**: M · **전략**: 완화
- **대응 계획**: While legacy screen 01 is live it can write `ATK` from `Math.random()` (D-I4) to any institution — including one the portal has just rotated with `SecureRandom`. The portal's key quality is therefore only as durable as the legacy screen's availability. Mitigation: legacy screens 00/01 disabled at deployment (T-I2-12); until then, treat any key whose rotation is not in the portal's audit trail as suspect
- **담당자**: PM (cutover owner) · **모니터링**: every sprint gate; mandatory at cutover
- **비고**: This is TM-I019 (concurrent legacy edit) sharpened to the credential. The audit trail is what makes it detectable: a portal-rotated key has an `institution.key.rotate` record, a legacy-written one has nothing
