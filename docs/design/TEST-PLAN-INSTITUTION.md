## 1. Test strategy

### 1.1 The governing principle for this module

The 로그인 plan's principle was *every control must demonstrably deny something*. Here the principle is narrower and sharper:

> **Every legacy control on this screen existed only in the browser. A test that drives the UI therefore proves nothing about enforcement.**

The duplicate check was a JS variable, the permission gate was an `alert()`, the 기관코드 format rule was a `fn_save()` branch, and the 인증키 was generated by `Math.random()` in the page. A UI-driven test of the legacy would have passed for every one of them while the server enforced none.

So: **every validation, authorization and uniqueness requirement is tested by a direct service call that bypasses the UI entirely.** UI tests verify usability; they are not evidence of enforcement.

The second principle follows from D-I1:

> **A write is not verified until it has been read back through the path that consumes it.**

Disable "worked" for four years because nobody re-queried the list. Every state-change test asserts the round trip.

### 1.2 Pyramid

| Level | Share | Focus |
|-------|-------|-------|
| Unit | ~55% | Masking, key generation, status enum, LIKE escaping, timestamp format, validation rules |
| Integration | ~35% | Mappers against a real PostgreSQL (Testcontainers), transactions, cascade, audit writes |
| E2E | ~10% | Five core operator journeys |

Integration share is high because the defects live in SQL and transaction boundaries, which unit tests cannot reach.

One test minimum per in-scope legacy defect. These are the tests that prove the port is a fix and not a faithful reproduction.

## 4. Negative-path security suite

The core of this plan — 22 tests, each proving a **refusal** or a **non-disclosure**.

| # | Test | Proves |
|---|------|--------|
| S-01…S-11 | Each admin endpoint called as a tenant user | 403 (TM-I001) |
| S-12 | Each admin endpoint called unauthenticated | 401 |
| S-13 | Availability endpoint enumerated 1,000× | No institution data; rate limit engages (TM-I002) |
| S-14 | Search response inspected | No full `ATK` (TM-I003) |
| S-15 | Create with an existing code | Existing row unchanged (TM-I004) |
| S-16 | Key reveal | Audit record written with actor and target (TM-I018) |
| S-17 | Key reveal as non-operator | 403 |
| S-18 | Update payload naming unowned columns | Those columns unchanged (TM-I015) |
| S-19 | Log scan across all institution operations | No `ATK`, no encrypted value (TM-I017) |
| S-20 | 기관코드 / 기관명 injection payloads | Bound parameters; no injection; output inert (TM-I010) |
| S-21 | Search with `pageSize=100000` | Clamped to 200 (TM-I011) |
| S-22 | Legacy-shape query `WHERE IS_STTS='Y'` after a logical delete | Deleted institution **absent** (ADR-INST-014 §2.1) |

S-22 is the one that would be easy to omit and matters most: it is the only automated evidence that our deletion semantics degrade safely for the legacy reader.

## 5. Legacy coexistence tests

New for this slice — verifying the boundary in [ADR-INST-016](adr/ADR-INST-016-legacy-coexistence.md).

| # | Test | Proves |
|---|------|--------|
| C-01 | Legacy `KKB_FT_FTIS_INFO_L001` SQL run verbatim after our writes | Rows readable, columns correctly populated |
| C-02 | Legacy list filtered `IS_STTS='Y'` / `'N'` after a logical delete | `'D'` row excluded from both |
| C-03 | Our update, then a full legacy column read | 30 unowned columns unchanged (rule 4) |
| C-04 | Cache notifier with the legacy endpoint unreachable | Operator informed, alert raised, change still committed |
| C-05 | Row created by the legacy screen, then edited by the portal | No data loss in either direction |

> **C-06 — "the send API refuses a disabled institution" — cannot be automated here.** The enforcement point is outside our boundary (TM-I013). It is a **manual cutover verification** owned by the PM under RISK-I02, and this plan states that explicitly rather than leaving a gap that looks covered.
