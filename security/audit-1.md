## 1. 차단 결함 / Blocking findings

### SEC-01 · HIGH · CVSS 7.5 · AES-256 키가 저장소에 하드코딩되어 있다

**위치** [application.yml:77](../src/main/resources/application.yml#L77)

```yaml
secret-key: ${IRIS_OTP_SECRET_KEY:E0lV/9B+V4JTWEk31kwKH46Jwfg9UqzfadjRLu43e4U=}
```

이 키는 `SecretCipher` 가 **OTP 비밀(`OTP_KEY`)을 복호화**하는 데 사용한다. 키를 가진 자는
저장된 모든 OTP 비밀을 복호화하고, 임의 사용자의 유효한 TOTP 코드를 생성할 수 있다 —
**2차 인증이 무력화된다.**

| 위반 항목 | 근거 |
|-----------|------|
| ADR-007 (키 관리) | 키는 환경변수/KMS 로만 주입 |
| CONST-SEC-L02 | 시크릿 하드코딩 금지 |
| harness §5 | "시크릿 0 — 모든 커밋" |
| 전자금융감독규정 | 암호키 관리 통제 |
| ISMS-P | 암호키 생명주기 관리 |

**바로 위 줄의 주석이 이 값을 금지하고 있다.** 즉 의도와 코드가 문서상으로 모순 상태다.

**중요**: 이 변경은 **의도된 것이라고 통보받았으므로 되돌리지 않았다.** 감사자로서 할 수
있는 것은 되돌리는 것이 아니라 **판정을 기록하는 것**이며, 판정은 REJECT 다.

**필요 조치** (순서대로)
1. 기본값 제거 → `application-local.yml`(git-ignored) 로 이동
2. **이 키를 폐기·재발급** — 커밋 이력에 남았다면 이미 유출된 것으로 간주해야 한다
3. 재발급 후 기존 암호문 재암호화 (키 회전 절차 필요)
4. `gitleaks` 규칙이 이 패턴을 잡지 못한 이유 조사 — L1 훅이 통과시켰다

> **L1 훅이 이것을 막지 못했다는 사실이 별개의 결함이다.** base64 32바이트 문자열은
> gitleaks 의 기본 규칙 집합에 걸리지 않는다. 훅이 있다는 것과 훅이 작동한다는 것은
> 다르다 — 이 프로젝트에서 세 번째로 확인된 같은 유형의 교훈이다.

## 2. 검증되지 않은 보안 전제 / Unverified security premises

### SEC-02 · 조건부 6.5 · 테넌트 격리의 근거가 확인되지 않았다 (AMB-M01)

테넌트 격리 전체가 "사용자를 이용기관에 연결하는 컬럼"에 의존한다. 그 컬럼을 **레거시
소스에서 확인할 수 없었다** — 추측으로 채우지 않고 `UserMapper.xml` 주석과 문서에
명시했다.

| 가정이 | 결과 |
|--------|------|
| 맞다면 | 격리 정상. CVSS 0 |
| 틀리다면 | **이용기관 담당자가 타 기관 문자내역을 조회** — CVSS 6.5, 개인정보보호법 위반 |

**중요한 점**: 이 상태에서는 **내가 작성한 모든 테넌트 테스트가 통과해도 의미가 없다.**
테스트는 코드가 의도대로 동작하는지 확인하지만, 그 의도의 전제가 틀렸는지는 확인하지
못한다. `qa/sql/explain-message-history.sql` §0 한 번 실행으로 답이 나온다.
