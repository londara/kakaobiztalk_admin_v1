## 1. 개요

### 1.1 왜 이 모델인가

DoD 1 은 "교차 검증 1회 이상 실행 (다른 LLM 벤더)" 을 요구한다. 이 환경에서 사용 가능한 외부 LLM CLI 를 확인한 결과 `codex`·`gemini`·`llm`·`aider` 모두 부재하고, **`ollama` 만 존재**했다. 보유 모델은 `qwen2.5-coder:7b` 단일.

이 선택은 차선이 아니라 **§2 S1 데이터 통제 관점에서는 최선**이다.

| S1 요구사항 | 충족 방식 |
|---|---|
| ① 시크릿·키·토큰 제거 | 투입 파일을 사전 스캔 후 선정. `application.yml`·`.env`(자격증명 보유, audit-S2a §3 참조)는 **투입 대상에서 제외** |
| ② 실데이터·PII 마스킹/제거 | 투입 파일에 실데이터·PII 없음(소스 코드). `ref.token()` 1건은 불투명 참조 토큰으로 시크릿 아님 — 확인 후 투입 |
| ③ 조직 승인 모델·리전 한정 | **모델이 로컬 프로세스에서 실행된다. 네트워크 egress 가 발생하지 않으므로 리전 문제가 성립하지 않는다** |

규제 데이터(신용정보·개인정보)를 다루는 프로젝트에서 "승인된 on-prem/사내 모델" 요건을 만족하는 가장 강한 형태다. 이전 회차 [cross-validation-3-intravendor.md](cross-validation-3-intravendor.md) 가 동일 벤더 내부 검증으로 대체했던 것과 달리, 이번 회차는 **벤더 독립성과 무-egress 를 동시에** 만족한다.

### 1.2 한계 — 먼저 명시한다

7B 파라미터 모델이다. 아래 §5 가 보여주듯 **오탐률 60% (5건 중 3건)** 이며, 특히 Java/Spring 의 `@Transactional` 의미론을 반복적으로 오해했다. 이 회차의 가치는 결함 목록의 정확성이 아니라, **파일 1개만 보고도 S2a 자체 결함 2건에 독립적으로 수렴했다**는 사실에 있다(§4.1). 위협모델·테스트·ADR·스프린트 로그를 전혀 보지 않은 관찰자가 같은 두 지점을 짚었다는 것은 그 두 결함이 코드 자체에서 읽히는 수준이라는 뜻이다.

### 1.3 프롬프트

명시적 결함 탐색 지시(§2 단계 2). 5개 축을 지정하고, 각 축에 대해 결함이 없으면 "no defect found" 라고 답하도록 요구했다. 온도 0.2, `num_ctx` 16384.

## 4. Claude 의 반박 / 보완 의견

### 4.1 채택 — 그리고 이것이 이 회차의 성과다

#### XV4-04 · 채택 · CVSS 6.5 `AV:N/AC:L/PR:L/UI:N/S:U/C:N/I:H/A:N`

**모델 주장**: `countAnywhere` 로 중복을 확인한 뒤 insert 하는데 동기화·락이 없다. 두 요청 사이에 같은 번호가 삽입되면 중복 검사는 통과하고 insert 가 실패한다.

**판정: 정확하다.** `SenderNumberWriteService.java:133-141` 은 전형적인 check-then-act 이며 READ COMMITTED 에서 두 동시 등록이 모두 0 을 보고 모두 insert 한다. 이는 `code-reviewer` 가 독립적으로 제기한 **CR-S2a-04** 와 동일한 결함이다 — 서로를 보지 못한 두 검토자가 같은 지점에 수렴했다.

**보완 (모델이 도달하지 못한 부분).** 모델은 "insert 가 실패한다" 에서 멈췄다. 실제 심각도는 그 다음에 있다:

1. 유일성을 실제로 막는 장벽은 `UX_KKB_DPNO_LDGR_01` (`V3__senderno_archive.sql:163`) 뿐이고, SPRINT-S2a-LOG §5 에 따르면 **이 인덱스는 어떤 환경에도 적용되어 있지 않다.** 따라서 **오늘 FR-SNDC-004 는 동시성 하에서 강제되지 않는다.**
2. `grep -rn "DuplicateKeyException\|DataIntegrityViolation" src/main/java` → **0건**. 인덱스가 적용되면 위반이 `handleUnexpected` 로 떨어져 **500 `INTERNAL_ERROR`** 가 되는데, 같은 업무 조건을 count 로 잡으면 **409 `DUPLICATE`** 다. 즉 G1 이후 동일한 운영자 행위가 타이밍에 따라 409 또는 500 이 된다.
3. 포털 내부에 동시성이 없어도 `AOA_ADMIN`(제2 작성자, RISK-S05)이 count 와 insert 사이에 행을 끼워넣을 수 있다.

`I:H` 근거 — 전역 유일성(AMB-S03)은 발신번호의 **권한 부여** 속성이다. 중복 등록은 두 기관이 같은 번호로 발송 가능한 상태를 만든다.

**권고**: `SenderNumberExceptionHandler` 에 `@ExceptionHandler(DuplicateKeyException.class)` 를 추가해 동일한 409 본문을 반환. count 검사는 빠른 경로로 유지.

#### XV4-02 · 부분 채택 · CVSS 2.7 (PR:L 4.2) `AV:N/AC:L/PR:H/UI:N/S:U/C:N/I:L/A:N`

**모델 주장**: `requireScopedInstitution` 이 세션 스코프를 확인하지만 **삭제되는 번호마다** 수행되지 않는다.

**관찰은 옳다. 기전 설명은 틀렸다.**

틀린 부분: *"검사는 실패하지만 트랜잭션은 그대로 커밋되어 번호가 삭제된 채 남는다"* — `AccessDeniedException` 은 `@Transactional` 경계 안에서 던져지므로 롤백된다. XV4-01 과 같은 오해다.

옳은 부분, 그리고 중요한 부분: **ref 별 재검증이 실제로 없다.** 그리고 `security-auditor`(SEC-S2a-06)와 `code-reviewer`(CR-S2a-02)가 독립적으로 더 강한 형태를 찾아냈다 — `requireScopedInstitution` 은 운영자에 대해 **항등함수**다. `requireOperator()` 가 두 줄 앞에서 비운영자를 전부 던져내므로, 이 지점에 도달한 시점에 `principal.operator()` 는 항상 true, 따라서 `effectiveInstitutionCode(requested)` 는 항상 `requested` 를 반환, 따라서 `!requested.equals(scoped)` 는 **항상 false**. `ACTION_TENANT_OVERRIDE_ATTEMPT` 감사 이벤트는 이 서비스에서 **기록될 수 없고** `AccessDeniedException` 은 **발생할 수 없다.**

**세 검토자 수렴.** 모델은 "번호별 검사 없음" 을, code-reviewer 는 "분기가 죽은 코드" 를, security-auditor 는 "위협모델 T-T8/T-T1 이 존재하지 않는 통제를 완화로 기재" 를 각각 찾았다. 같은 결함의 세 층이다.

`I:L` 근거 — 권한 상승이 아니다. 운영자는 설계상 기관 간 쓰기 권한을 가진다(FR-TEN-003). 손실된 것은 **탐지 통제**이며, 위협모델·스프린트 로그의 보안 94점·G3 증거 패키지가 모두 이를 작동하는 것으로 credit 하고 있다.

**권고**: audit-S2a §10 조건 1 과 동일 — T-T8/T-T1 을 개정해 롤 게이팅뿐임을 명시하고 죽은 분기를 제거하거나, 세션 기록 기관과 ref 의 일치를 요구해 실재화. 둘 중 하나. 현 상태 유지는 금지 — `V3__senderno_archive.sql:43` 이 "D-S1 의 가족" 이라 부르는 실패 양식 그대로다.

### 4.2 반박

#### XV4-01 · 반박 · 오탐

**주장**: `deleteLive` 실패 시 트랜잭션이 커밋되어 archive 가 반쯤 적용된다.

**근거 있는 반박**: `SenderNumberWriteService#delete` 는 `:180` 에서 `@Transactional` 이며 `archive`→`deleteLive`→`insertHistory` 세 문장이 **모두 그 경계 안**에서 실행된다. 루프 안에서 중첩 트랜잭션을 열지 않는다. `deleteLive` 가 던지면 `archive` 의 insert 를 포함해 롤백된다. code-reviewer 가 이를 명시적으로 검증했다 — *"archive 가 성공한 뒤 던질 수 있는 문장은 `deleteLive` 와 `insertHistory` 뿐이며 둘 다 같은 경계 안이다. **아카이브가 채워진 채 원장 행이 남는 롤백 경로는 없다.**"* 또한 발신번호 매퍼 전체가 기본 `SqlSessionFactory` 로 해석되므로(유일한 커스텀 팩토리 `bulkSqlSessionFactory` 는 `BulkAggregateMapper` 만 등록) 주 트랜잭션 매니저가 세 문장을 실제로 덮는다.

모델은 `@Transactional` 어노테이션이 있음에도 실패 시 커밋을 가정했다. Spring 의 기본 롤백 규칙(런타임 예외 → 롤백)을 적용하지 못한 것으로 보인다.

**다만 모델이 가리킨 영역에는 실제 결함이 있고, 모델은 그것을 놓쳤다.** `code-reviewer` CR-S2a-05: `audit.record(..., Outcome.OK, ...)` 가 `@Transactional` **안**에서 호출되고 `AuditService.record` 는 `REQUIRES_NEW` 이므로, 감사 행이 업무 트랜잭션보다 **먼저 독립 커밋**된다. 이후 외부 커밋이 실패하면 감사 저장소에는 *"3건 삭제"* + outcome OK 가 남고 실제로는 아무것도 삭제되지 않는다. **분기된 저장소는 업무 테이블이 아니라 감사 테이블이다.** 모델의 직관("반쯤 적용된 상태가 남는다")은 옳은 방향이었고 대상을 틀렸다.

#### XV4-03 · 반박 · 사실 오류

**주장**: `deleteLive` 는 row count 0 만 검사하고 > 1 검사가 없다.

**반박**: 코드는 반대다. `SenderNumberWriteService:217-229` 는 `deleteLive` 의 결과를 **0 과 > 1 양쪽** 검사한다. 정확히 검사가 한쪽뿐인 문장은 **`archive`** (`:204-214`, `== 0` 만) 이며, 이는 code-reviewer 의 **CR-S2a-07** 이다 — 형제 문장들은 모두 정확한 개수를 본다(`insertLedger` `!= 1`, `insertHistory` `!= 1`, `deleteLive` 0 및 >1).

모델은 결함이 있는 메서드를 옳게 짚지 못한 채 결함 유형만 맞혔다. 채택하지 않는다 — 주장된 위치에 주장된 결함이 없다. **CR-S2a-07 로 별도 추적**한다.

#### XV4-05 · 반박 · 오탐

**주장**: `writeHistory` 실패 시 `IllegalStateException` 이 영향 행 수를 포함하므로 DB 행 수를 추론할 수 있다.

**반박**: 메시지에 담기는 값은 **해당 문장 자신이 영향을 준 행 수**이며 실질적으로 0 또는 1 이다. 테이블 크기·다른 행의 존재·기관별 건수에 대해 어떤 정보도 담지 않는다. `count(*)` 결과가 아니다. 또한 이 예외는 500 으로 매핑되고 본문은 `{code, message}` 고정 형태이므로 클라이언트가 받는 것은 행 수가 아니다.

정보 노출 축에서 S2a 쓰기 경로는 실제로 깨끗하다 — audit-S2a §4 가 싱크별로 검증했다. **모델이 이 축에서 "no defect found" 라고 답해야 했던 자리에 결함을 만들어냈다.** 오탐으로 명시 기록한다.

## 7. 본 검증의 한계

1. **모델 역량.** 7B. 오탐 60%. 대규모 상용 모델(Codex/GPT-5/Gemini)의 대체물로 동등하다고 주장하지 않는다.
2. **투입 범위 1개 파일.** `SenderNumberWriteService.java` 만 투입했다. 컨트롤러·매퍼 XML·V3 DDL·프론트는 교차검증되지 않았다. 컨텍스트 예산(16K)과 모델 역량을 고려한 선택이며, 거래 무결성·인가가 집중된 파일을 골랐다.
3. **시크릿 보유 파일 미투입.** `application.yml`·`.env` 는 S1 통제에 따라 제외했다. 결과적으로 **이번 릴리즈를 실제로 차단한 3건은 교차검증 대상이 아니었다.** 이는 통제의 정상 작동이지만, 시크릿 결함은 교차검증으로 잡을 수 없다는 구조적 한계를 뜻한다 — 그 층은 L1/L2 Hook 의 몫이고, 그 Hook 이 작동하지 않았다(SEC-S2a-04).
4. **테스트 코드 미투입.** 모델은 어떤 결함이 이미 회귀 시험으로 닫혔는지 알 수 없었다. XV4-02/-04 가 실제 미결 결함이었던 것은 다행이나 구조적 보장은 아니다.
