# Skill 07 — ការផ្ទៀងផ្ទាត់ការអនុលោមតាមស្តង់ដារ (Validate Standard)

> **គោលបំណង**: ផ្ទៀងផ្ទាត់ថា harness ស្តង់ដារខ្លួនឯង ឬគម្រោងដែលបានអនុវត្ត harness បំពេញតាមរចនាសម្ព័ន្ធចាំបាច់ និងរបាំងការពារ។
> **លក្ខណៈ**: មិនមែនជាដំណាក់កាលអភិវឌ្ឍន៍លីនេអ៊ែរទេ តែជាជំនាញសវនកម្មដែលដំណើរការឡើងវិញច្រើនដង។
> **គោលការណ៍**: មិនប្រើលំហូរបង្កើតដំបូងផ្អែកលើ seed.yaml / bootstrap ទេ។ វិនិច្ឆ័យផ្អែកលើផលិតផលដែលកើតពី Skill និងស្ថានភាពឯកសារពិត។

## 📘 សេចក្តីពន្យល់សង្ខេប (សូមអានមុនគេ)

**ជំនាញនេះធ្វើអ្វី?**
Skill 01~06 គឺជាដំណើរការ **សាងសង់**។ Skill 07 គឺជា **អធិការកិច្ច** — វាពិនិត្យថាតើអ្នកបានធ្វើតាមស្តង់ដារពិតប្រាកដឬអត់។

**លក្ខណៈពិសេសសំខាន់បំផុត — អានតែប៉ុណ្ណោះ (Read-only):**
ជំនាញនេះ **មិនកែឯកសារ ឬកូដទេ**។ វាគ្រាន់តែរាយការណ៍ថាមានអ្វីខុស។ ហេតុអ្វី? ដើម្បីរក្សាភាពជាកណ្តាលនៃអធិការកិច្ច — អ្នកត្រួតពិនិត្យមិនគួរជាអ្នកកែបញ្ហាដែលខ្លួនរកឃើញនោះទេ។ ការកែជាការងារដាច់ដោយឡែក (សូមមើល Skill 08)។

**របៀបប្រើ:** ដំណើរការវា **មុនច្រក G1/G2/G3 នីមួយៗ** ដើម្បីដឹងជាមុនថាតើនឹងឆ្លងឬអត់។

**របាំងសំខាន់មួយ — ស្រទាប់ភស្តុតាង ៣ កម្រិត (§3.0):**
មិនមែនភស្តុតាងទាំងអស់មានទម្ងន់ស្មើគ្នាទេ។
- **កម្រិត ១ (វត្ថុវិស័យ)** — ឯកសារមាន/គ្មាន, លទ្ធផលឧបករណ៍, ចំនួន → អាចផ្ទៀងផ្ទាត់ឡើងវិញបាន
- **កម្រិត ២ (ពាក់កណ្តាលវត្ថុវិស័យ)** — ការផ្ទៀងផ្ទាត់ដោយ AI ក្រុមហ៊ុនផ្សេង + ពិន្ទុ CVSS ផ្លូវការ
- **កម្រិត ៣ (មានភាពប្រធានបទ)** — ពិន្ទុ ៧ វិមាត្រដែល AI ដាក់ឱ្យខ្លួនឯង

**ច្បាប់ដាច់ខាត: ការទប់ស្កាត់វឌ្ឍនភាព (FAIL) អាចប្រើបានតែភស្តុតាងកម្រិត ១ និង ២ ប៉ុណ្ណោះ។** ពិន្ទុវាយតម្លៃខ្លួនឯងរបស់ AI មិនអាចជាមូលហេតុតែមួយគត់ដើម្បីទប់ស្កាត់នោះទេ។

**វាក្យសព្ទសំខាន់ៗ:**

| ពាក្យ | ន័យ |
|------|-----|
| Package mode | របៀបផ្ទៀងផ្ទាត់ **កញ្ចប់ harness ខ្លួនឯង** (ភាពស៊ីសង្វាក់ខាងក្នុង) |
| Project mode | របៀបផ្ទៀងផ្ទាត់ **គម្រោងពិត** ដែលកំពុងប្រើ harness |
| PASS / WARN / FAIL | ឆ្លង / ព្រមាន (ដំណើរការបាន តែគួរកែ) / ធ្លាក់ (ទប់ស្កាត់ច្រក) |
| Drift | ការរសាត់ — ពេលឯកសារនិយាយមួយយ៉ាង តែឯកសារពិតជាមួយយ៉ាងទៀត |
| Orphan | ធាតុកំព្រា — គ្មានការភ្ជាប់ទៅអ្វីទាំងអស់ |
| Deprecated alias | ឈ្មោះចាស់ដែលឈប់ប្រើ (ឧ. `java-porter`) ដែលមិនគួរនៅសល់ |
| Historical mention | ការលើកឡើងក្នុងឯកសារប្រវត្តិសាស្ត្រ — មិនរាប់ជា FAIL ព្រោះវាពិពណ៌នាអតីតកាល |
| False Positive | ការរាយការណ៍ខុស — ត្រូវកត់ត្រាជាករណីលើកលែងព្រមទាំងមូលហេតុ |
| Gate Decision | សេចក្តីសម្រេចថាតើអាចចូលច្រក G1/G2/G3 បានឬអត់ |

**លទ្ធផលចុងក្រោយ:** របាយការណ៍តែមួយ `reviews/standard-validation-{YYYYMMDD}.md` មាន ៤ ផ្នែក៖ សេចក្តីសង្ខេប · ពិន្ទុ · បញ្ហារកឃើញ · សេចក្តីសម្រេចអំពីច្រក។

## 1. ការកំណត់របៀបដំណើរការ

ត្រូវកំណត់របៀបជាមុនសិន នៅក្នុងថតបច្ចុប្បន្ន តាមលក្ខណៈវិនិច្ឆ័យខាងក្រោម។

| របៀប | លក្ខណៈវិនិច្ឆ័យ | គោលបំណង |
|------|----------|------|
| Package mode | មាន `.claude/skills/`, `templates/`, `hooks/`, `scripts/`, `HARNESS-PROCESS-STANDARD.md` | ផ្ទៀងផ្ទាត់កញ្ចប់ harness ស្តង់ដារខ្លួនឯង |
| Project mode | មាន `docs/`, `src/` ឬផលិតផលគម្រោង + បានអនុវត្តទ្រព្យសម្បត្តិ harness មួយផ្នែក | ផ្ទៀងផ្ទាត់ស្ថានភាពអនុវត្តក្នុងគម្រោងពិត |

បើការកំណត់មិនច្បាស់លាស់ ត្រូវបង្ហាញបេក្ខភាពទាំង Package mode និង Project mode ហើយកត់ត្រាក្នុងរបាយការណ៍ថាបានផ្ទៀងផ្ទាត់តាមលក្ខណៈវិនិច្ឆ័យណា។

## 2. វិសាលភាពនៃការផ្ទៀងផ្ទាត់

### 2.1 បញ្ជីសារពើភណ្ឌកញ្ចប់

- មានជំនាញ ៨: `01-plan-project` ~ `06-finalize-deliverables`, `07-validate-standard`, `08-harness`
- គ្រប់ជំនាញ (01~07, 08-harness) មាន frontmatter `lead_agent` និង `support_agents` ហើយត្រូវគ្នានឹងឯកសារភ្នាក់ងារពិត
- តារាង Skill catalog ក្នុង README / PACKAGE-INDEX / PROCESS ត្រូវគ្នានឹង lead/support ក្នុង frontmatter នៃ SKILL នីមួយៗ
- មានភ្នាក់ងារស្តង់ដារ ១៣ និងមាន frontmatter
- ទ្រព្យសម្បត្តិដែលកំពុងចែកចាយ (គំរូ / CSV ឧទាហរណ៍ / ឯកសារភ្នាក់ងារសកម្ម) ត្រូវគ្នានឹងឈ្មោះភ្នាក់ងារស្តង់ដារបច្ចុប្បន្ន (`backend-developer`, `frontend-developer`, `qa-engineer`) ហើយឈ្មោះក្លែងដែលឈប់ប្រើ (`java-porter`, `parity-tester`) មិននៅសល់
- មានគំរូផលិតផល ២១
- មាន Security Hook ៣ កម្រិត: L1 pre-commit, L2 CI, L3 prod gate
- ឯកសារជំនួយដែល Hook / Script / CI យោងទៅ (ដូចជា `hooks/gitleaks.toml`) មានពិតប្រាកដក្នុងកញ្ចប់
- មាន script ប្រតិបត្តិការ: `parity-check.sh`, `generate-codecs.sh`
- ចំនួនជំនាញក្នុងឯកសារ README / PACKAGE-INDEX / WORKFLOW / PROCESS ត្រូវគ្នានឹងមែកធាងឯកសារពិត

### 2.2 លំហូរការងារ និងច្រក

- តើលក្ខខណ្ឌចូល, ផលិតផលចេញ និង DoD របស់ Skill 1~6 ត្រូវបានបញ្ជាក់ក្នុងឯកសារឬទេ
- ពាក្យបញ្ជាចាប់ផ្តើមរហ័សក្នុង README / PACKAGE-INDEX / PROCESS / WORKFLOW អនុវត្តតាមលំដាប់ បង្កើត `docs/` រួច `git init` រួចដំឡើង Hook យ៉ាងស៊ីសង្វាក់
- តើមានច្រក G1 វិភាគ, G2 រចនា, G3 ចេញផ្សាយឬទេ
- តើអ្នកអនុម័ត និងផលិតផលចាំបាច់នៃច្រកនីមួយៗច្បាស់លាស់ឬទេ
- តើ `07-validate-standard` ត្រូវបានចងក្រងជាឯកសារថាជាជំនាញផ្ទៀងផ្ទាត់ដែលអាចដំណើរការភ្លាមៗក្រោយ setup និងមុនច្រកនីមួយៗឬទេ
- តើលក្ខណៈវិនិច្ឆ័យបង្កើតសំណួរសម្រាប់មនុស្ស (CQ1~CQ3, §4.8) ត្រូវបានកំណត់និយមន័យ ហើយសំណុំសំណួរថេរ (០១ ១២ សំណួរ · ០៦ ៧ សំណួរ) ត្រូវបានដាក់ស្លាកតាមលក្ខណៈវិនិច្ឆ័យនោះឬទេ

### 2.3 រចនាសម្ព័ន្ធ Team-with-Leader

- ភ្នាក់ងារ `_team-leader` មានការទទួលខុសត្រូវលើ ការវិភាគ DAG, ការចែក task, ការសម្របសម្រួលការប៉ះទង្គិច, ការវាយតម្លៃ ៧ វិមាត្រ និងការរាយការណ៍ PM
- frontmatter របស់ភ្នាក់ងារនីមួយៗមាន `write_dirs`
- ករណីមានភ្នាក់ងារច្រើនសរសេរក្នុងថតតែមួយ ត្រូវសម្គាល់ជា WARN។ ប៉ុន្តែថតផលិតផលរួមដែលមានចេតនា អាចដោះស្រាយជាករណីលើកលែងបើមានមូលដ្ឋាន
- មានច្បាប់ទំនាក់ទំនង/រាយការណ៍ TEAM_CHANNEL / DIRECT / LEADER_BROADCAST ឬសមមូល

### 2.4 របាំងការពារ និង Security Hook

- តើ L1 Hook ដំណើរការ gitleaks ហើយពេលឆ្លងកាត់ តើទាមទារឯកសារភស្តុតាងអនុម័តឬទេ
- តើ L2 CI អនុវត្ត gitleaks, ការស្កេនភាពអាស្រ័យ និង SAST ឬទេ
- តើដំណាក់កាលសវនកម្ម AI នៅ L2 ឆ្លងកាត់ដោយស្ងាត់ស្ងៀមក្នុងស្ថានភាព `TODO` ឬទេ
- តើ L3 prod gate ទាមទារការអនុម័តពី PM + សន្តិសុខព័ត៌មាន + ប្រតិបត្តិការឬទេ
- តើកំហុស CVSS >= 7.0 ត្រូវបានបញ្ជាក់ជាលក្ខខណ្ឌទប់ស្កាត់ការចេញផ្សាយឬទេ
- មានលក្ខណៈវិនិច្ឆ័យ REJECT ដូចជា សម្ងាត់, កំណត់ហេតុ PII ជាអត្ថបទធម្មតា, ការអ៊ិនគ្រីបខ្សោយ, ការឆ្លងកាត់ការផ្ទៀងផ្ទាត់អត្តសញ្ញាណ, SQL Injection

### 2.5 ភាពតាមដានបាន និងផលិតផល

- តម្រូវការមានប្រព័ន្ធ REQ-ID
- មានច្បាប់តាមដាន `// source:` ឬ `// req:`
- មានកាតព្វកិច្ចសរសេរ ADR និងគំរូ ADR
- មាន trace matrix ឬផលិតផលផ្គូផ្គងតម្រូវការ-កូដសមមូល
- មានផលិតផល Sprint log, review report, security audit, cross-validation, runbook

### 2.6 គុណភាព និងការវាយតម្លៃ

- លក្ខណៈវិនិច្ឆ័យ និងកម្រិតកំណត់នៃការវាយតម្លៃ ៧ វិមាត្រ ត្រូវបានបញ្ជាក់
- មានរង្វិលជុំបំពេញបន្ថែមពេលក្រោម ៩០ ពិន្ទុ និង escalation ទៅ PM ក្រោយ ៥ ដង
- ទម្ងន់ ៧ វិមាត្រ · កម្រិតកំណត់ ៩០ · ៥ ដង ស្នងតាមលក្ខណៈវិនិច្ឆ័យ §4.6/§4.9 (`[មូលដ្ឋាន:ការពិនិត្យឡើងវិញ sg-gw · អាចកែសម្រួលបាន]`) ហើយពេលគម្រោងកែសម្រួល តើមូលដ្ឋានត្រូវបានកត់ត្រាក្នុង ADR/ការពិនិត្យឡើងវិញឬទេ
- Skill 5 កាត់បន្ថយការលើកតម្កើងខ្លួនឯង តាមរយៈការវាយតម្លៃឡើងវិញដោយឯករាជ្យ ឬការផ្ទៀងផ្ទាត់ឆ្លង
- លក្ខខណ្ឌ coverage សាកល្បង / ការវិភាគស្ថិតិ / ការស្កេនភាពអាស្រ័យ / ការផ្ទៀងផ្ទាត់ parity ត្រូវបានកំណត់និយមន័យសមស្របនឹងលក្ខណៈគម្រោង

### 2.7 ការរសាត់ (Drift) និងទ្រព្យសម្បត្តិហួសសម័យ

- ករណីចំនួនឯកសារ, ចំនួនជំនាញ, ទីតាំង ដែលនៅសល់ក្នុងឯកសារ ខុសពីឯកសារពិត → WARN
- បើវិធីបង្កើតបែបចាស់ដូចជា `seed.yaml`, ការសន្មត bootstrap, script ប្រើ v2-team លាយឡំក្នុងលំហូរផ្អែកលើ Skill បច្ចុប្បន្ន → WARN
- បើការចាត់តាំង Skill owner ខ្វះ ឬយោងទៅភ្នាក់ងារដែលមិនមាន → FAIL
- បើឯកសារដេរីវេដូចជា HTML ដែលបង្កើតឡើង គ្មាន, ចាស់ជាងប្រភព Markdown, ឬខ្លឹមសារមិនស៊ីគ្នា → WARN
- ប៉ុន្តែឯកសារប្រវត្តិសាស្ត្រដូចជា `reviews/`, `docs/plans/`, `docs/specs/` អាចពិពណ៌នាស្ថានភាពអតីតកាល ដូច្នេះការលើកឡើងជាប្រវត្តិសាស្ត្រតែម្នាក់ឯង មិនត្រូវចាត់ជា FAIL ទេ

## 3. លក្ខណៈវិនិច្ឆ័យវិនិច្ឆ័យ

### 3.0 ស្រទាប់នៃភាពវត្ថុវិស័យនៃមូលដ្ឋានវិនិច្ឆ័យ

មូលដ្ឋាននៃការវិនិច្ឆ័យអនុលោមភាព មាន ៣ ស្រទាប់ដែលមានកម្រិតវត្ថុវិស័យខុសគ្នា ហើយ **ការទប់ស្កាត់វឌ្ឍនភាព (FAIL · CVSS≥7.0) ត្រូវប្រើតែមូលដ្ឋានស្រទាប់ ១ និង ២ ប៉ុណ្ណោះ**។

| ស្រទាប់ | មូលដ្ឋាន | ភាពវត្ថុវិស័យ | ឧទាហរណ៍ |
|------|------|--------|----|
| 1. ការផ្ទៀងផ្ទាត់ដោយម៉ាស៊ីន | ឯកសារមាន/គ្មាន · grep · តួលេខឧបករណ៍ CI · ភស្តុតាងច្រក | **វត្ថុវិស័យ** (អាចធ្វើឡើងវិញបាន) | ចំនួនជំនាញ/ភ្នាក់ងារ/គំរូ, gitleaks ០ ករណី, ArchUnit/coverage, អ្នកអនុម័ត+កាលបរិច្ឆេទ |
| 2. ការផ្ទៀងផ្ទាត់ឯករាជ្យខាងក្រៅ | ការផ្ទៀងផ្ទាត់ឆ្លងដោយ LLM ក្រុមហ៊ុនផ្សេង + **រូបមន្តផ្លូវការ CVSS v3.1** | ពាក់កណ្តាលវត្ថុវិស័យ (រង្វាស់ជាស្តង់ដារទទួលស្គាល់) | ពិន្ទុកំហុសពី cross-validation |
| 3. ការវាយតម្លៃខ្លួនឯងដោយ AI | ពិន្ទុ ៧ វិមាត្រ ។ល។ | មានភាពប្រធានបទ (§4.9 `[sg-gw · អាចកែសម្រួលបាន]`) | ការដាក់ពិន្ទុភាពងាយអាន · ភាពពេញលេញ — **ជាសូចនាករយោង មិនមែនជាមូលដ្ឋានទប់ស្កាត់តែម្នាក់ឯងទេ**។ ការកាត់បន្ថយ: ការវាយតម្លៃឡើងវិញដោយឯករាជ្យនៅ Skill 5 (គម្លាត>10→PM) · ច្រកមនុស្ស |

| កម្រិត | អត្ថន័យ | ការដោះស្រាយ |
|------|------|------|
| PASS | បំពេញលក្ខខណ្ឌចាំបាច់ | អាចបន្តទៅជំហានបន្ទាប់ |
| WARN | ដំណើរការបាន ប៉ុន្តែមានការរសាត់ពីស្តង់ដារ ឬត្រូវការការបញ្ជាក់ដោយដៃ | ណែនាំឱ្យបំពេញមុនច្រក |
| FAIL | ខ្វះរបាំងការពារចាំបាច់ ឬផលិតផលចាំបាច់ | ទប់ស្កាត់ការចូលច្រកពាក់ព័ន្ធ |

លក្ខខណ្ឌ FAIL ភ្លាមៗ:
- ខ្វះច្រកចាំបាច់ G1/G2/G3
- ខ្វះ Security Hook ក្នុងចំណោម L1/L2/L3 ដែលគម្រោងនោះត្រូវការ
- សវនកម្ម AI នៅ L2 ត្រូវបានចាត់ទុកជាជោគជ័យទាំងស្ថានភាព TODO
- មានកំហុស CVSS >= 7.0 ដែលមិនទាន់ដោះស្រាយ
- ការឆ្លងកាត់ការស្កេនរកសម្ងាត់ត្រូវបានអនុញ្ញាតដោយគ្មានភស្តុតាងអនុម័ត
- គ្មានគោលនយោបាយអនុម័តសម្រាប់សកម្មភាពបំផ្លិចបំផ្លាញដូចជា ប្រតិបត្តិការ/DB/ការលុប/force-push

## 5. គោលការណ៍ដំណើរការ

- មិនកែកូដ ឬឯកសារដោយស្វ័យប្រវត្តិទេ។ ការកែត្រូវបំបែកជាការងារដាច់ដោយឡែក។
- ទីតាំងដែលរកឃើញ ត្រូវកត់ត្រាជាទីតាំងឯកសារ និងលេខបន្ទាត់ តាមដែលអាចធ្វើបាន។
- ក្នុង Package mode មើលភាពស៊ីសង្វាក់ខាងក្នុងនៃកញ្ចប់ស្តង់ដារ។
- ក្នុង Project mode មើលផលិតផលគម្រោង និងលទ្ធភាពឆ្លងច្រក។
- បើលក្ខណៈវិនិច្ឆ័យផ្ទៀងផ្ទាត់មិនសមនឹងលក្ខណៈគម្រោង ត្រូវបន្ទាបពី FAIL ទៅ WARN ហើយដាក់ជាធាតុសម្រាប់ PM វិនិច្ឆ័យ។

## 6. លក្ខណៈវិនិច្ឆ័យបញ្ចប់ (DoD)

- [ ] បានសរសេររបាយការណ៍ `reviews/standard-validation-{YYYYMMDD}.md` (រួមទាំង Summary / Score / Findings / Gate Decision)
- [ ] រាល់ Finding មានកម្រិត (FAIL/WARN/NOTE) · ទីតាំង (ឯកសារ:បន្ទាត់) · វិធានការណែនាំ
- [ ] បញ្ជាក់ថា FAIL មាន ០ ករណី ឬបញ្ជាក់មូលហេតុទប់ស្កាត់ច្រកតាម FAIL នីមួយៗ
