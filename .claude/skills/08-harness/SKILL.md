# Harness Assistant — 검증 보완 가이드 (07 후속)

> **위치**: 개발 흐름의 마지막 보조 스킬. **01~06 개발 → 07 표준 검증 → 08 보완 가이드** 순서.
> **목적**: 07 검증 결과를 받아 **보완할 내용을 우선순위로 가이드**하고(주), 진행 중 프로젝트의 다음 행동을 안내한다(부).
> **원칙**: 기존 자산(01~07 스킬·에이전트·템플릿) **무변경 재사용**. 본 스킬은 디스패처 + 상태 관리만 담당.
> **설계서**: `docs/specs/2026-06-12-harness-assistant-design.md`

---

## 0. 담당 에이전트

| 역할 | 에이전트 | 책임 |
|------|----------|------|
| Lead | `team-leader` | 모드 분기, 상태파일 관리, 진입 판정, 액션플랜 통합 보고 |
| Support | `code-reviewer` | 감사 모드에서 /07 결과 검토와 보완 적용분 품질 확인 |
| Support | `docs-writer` | 액션플랜·진행 안내 문서화, 상태파일 기록 정리 |

> Lead 에이전트는 두 모드의 결과를 단일 보고로 통합한다. 게이트 결재는 사람 전용(§4.8 CQ3).

---

## 1. 모드 선택

인자가 없으면 사용자에게 1회 질문한다 (CQ1 — 흐름 분기의 필수 입력):

> ① **표준 준수 감사** — 현재 디렉터리의 표준 준수를 점수화하고 보완을 가이드
> ② **신규 프로젝트 진행** — 01~06 스텝별 진행 안내 (상태추적)

인자 지원: `/08-harness audit` → ①, `/08-harness new` → ②.
모드 판별이 모호하면 07 §1 의 Package/Project 판별 규칙을 재사용한다.

## 2. [A] 감사 모드

```
[A-1] /07-validate-standard 실행 (읽기전용 — 07 원칙 보존)
   ▼
[A-2] reviews/standard-validation-*.md 최신본 파싱
   │    파싱 실패 시 → 원문 리포트 제시 + 수동 안내로 강등 (진행을 막지 않음)
   ▼
[A-3] 보완 액션플랜 생성 — 아래 표 형식
   ▼
[A-4] 항목별 대화형 적용 (1건씩: 적용/건너뜀/백로그 — CQ3)
   │    승인분만 수정, 항목별 변경 요약 제시
   │    ⚠ /07 스킬 자체는 수정 금지 (읽기전용 원칙)
   ▼
[A-5] /07 재실행 → before/after 점수 비교 보고
   ▼
[A-6] (상태파일 있으면) last_audit 갱신
```

### 액션플랜 표 형식

| 순위 | ID | 심각도 | 무엇 | 어디(파일:라인) | 왜(근거/규정) | 권고 조치 | 작업량 |
|------|----|--------|------|----------------|---------------|-----------|--------|

### 우선순위 규칙

1. **FAIL(게이트 차단) → WARN(게이트 전 권고) → LOW(백로그)**
2. 동급 내: **보안 > 추적성 > 문서**

## 3. [B] 신규 프로젝트 모드

```
[B-1] docs/.harness-state.yaml 읽기
   │    없으면 → Setup §0 체크(패키지 복사·git init·L1 훅) 안내 후
   │             templates/implementation/HARNESS-STATE.template.yaml 로 생성 제안
   ▼
[B-2] 상태파일 + 실제 산출물 교차 확인 (파일이 진실)
   │    불일치 → 실제 파일 기준 교정 제안 (사용자 확인 후 수정)
   ▼
[B-3] 진입 판정 테이블(§3.1)로 다음 행동 결정
   │    충족 → "다음: /0X 진입 가능 — 진행할까요?"
   │    게이트 미결재 → "차단: GX 결재 대기" + 기록 방법 안내 (진행 강행 금지)
   ▼
[B-4] 사용자 승인 시 해당 /0X 스킬로 진입 (기존 스킬 그대로)
   ▼
[B-5] 스텝 완료 시 상태파일 갱신 (steps.0X = done, outputs_verified, at)
```

### 3.1 진입 판정 테이블

| 다음 스텝 | 요구 조건 (산출물 + 게이트) |
|-----------|------------------------------|
| 01 | (없음 — Setup §0 완료 권장) |
| 02 | `docs/planning/PROJECT-PROPOSAL.md` 존재 |
| 03 | `docs/requirements/REQUIREMENTS-SPEC.md` + **G1 approved** |
| 04 | `docs/design/DEV-PLAN.md`·`TEST-PLAN.md`·`adr/ADR-001-tech-stack.md`·`threat-model.md` + **G2 approved** |
| 05 | Sprint 종료 (`docs/sprints/SPRINT-N-LOG.md` 존재) |
| 06 | **G3 approved** |

### 3.2 게이트 규칙 (강제)

- 게이트 `approved` + `approver` 는 **사람이 직접 기록** — 본 스킬은 기록 방법만 안내한다. AI 임의 승인 금지 (§4.8 CQ3, 게이트 우회 금지).
- G1/G2/G3 진입 직전에는 `/07` 실행을 자동 권고한다 (07 when_to_use 와 일치).

## 4. 에러·엣지 처리

| 상황 | 처리 |
|------|------|
| 상태파일 없음 | [B-1] 생성 제안 |
| 상태파일 손상/불일치 | 실제 산출물 기준 재구성 제안 (사용자 확인 후) |
| /07 리포트 파싱 실패 | 원문 제시 + 수동 안내로 강등 |
| `harness_version` ≠ 패키지 버전 | 감사 모드 실행 권고 (drift) |
| Package/Project 모드 모호 | 07 §1 판별 규칙 재사용, 판단 근거를 보고에 남김 |

## 5. 완료 기준 (DoD)

- [ ] (감사) 액션플랜 제시 + 승인분 적용 + before/after 점수 보고
- [ ] (감사) /07 스킬·리포트 원본 무변경 (적용은 별도 쓰기 단계)
- [ ] (신규) 다음 행동 1개를 명확히 제시 (진입 가능 / 차단 사유 + 해소 방법)
- [ ] (신규) 게이트 결재를 AI 가 기록하지 않음 — 안내만
- [ ] 상태파일 갱신 시 실제 산출물과 일치 확인

## 6. 질의 기준

본 스킬의 사용자 질문은 §4.8 기준을 따른다: 모드 선택·스텝 진입 승인 = **CQ1**, 보완 적용 여부·게이트 진행 = **CQ3**. 결함 신호 없는 질문은 생성하지 않는다.
