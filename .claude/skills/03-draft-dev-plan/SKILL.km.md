# Skill 03 — ការសរសេរផែនការអភិវឌ្ឍន៍ + ផែនការសាកល្បង

> **គោលបំណង**: បំបែកតម្រូវការ → Epic / Sprint / Task + សម្រេចចិត្តលើ tech stack + បង្កើតយុទ្ធសាស្ត្រសាកល្បង។
> **រយៈពេល**: ១~៣ ថ្ងៃ
> **លក្ខខណ្ឌមុន**: Skill 2 (ការអនុម័ត REQUIREMENTS-SPEC.md)
> **ជំហានបន្ទាប់**: Skill 4 (ការអនុវត្ត)

## 📘 សេចក្តីពន្យល់សង្ខេប (សូមអានមុនគេ)

**ជំនាញនេះធ្វើអ្វី?**
Skill 02 ប្រាប់ថា "ត្រូវសាងសង់អ្វី"។ Skill 03 សម្រេចថា **"សាងសង់ដោយរបៀបណា"** — ជ្រើសបច្ចេកវិទ្យា រៀបចំរចនាសម្ព័ន្ធ បែងចែកការងារជា Sprint និងកំណត់របៀបសាកល្បង។

**ចំណុចសំខាន់បំផុត ៣:**
1. **ការសម្រេចចិត្តលើបច្ចេកវិទ្យាត្រូវមានភស្តុតាង** — មិនអាចនិយាយត្រឹម "ខ្ញុំចូលចិត្ត Spring Boot"។ ត្រូវប្រៀបធៀបយ៉ាងតិច ២ ជម្រើស តាមលក្ខណៈវិនិច្ឆ័យ ៦ ដែលមានទម្ងន់ រួចកត់ត្រាជា ADR។
2. **ការធ្វើគំរូគំរាមកំហែង (Threat Model)** — គិតពីវិធីវាយប្រហារ **មុនពេលសរសេរកូដ** មិនមែនក្រោយ។ ប្រើក្របខណ្ឌ STRIDE។
3. **បញ្ជីហានិភ័យ ≥ ១០ ករណី** — បង្ខំឱ្យគិតជាមុនអំពីអ្វីដែលអាចខូច។

**វាក្យសព្ទសំខាន់ៗ:**

| ពាក្យ | ន័យ |
|------|-----|
| ADR | Architecture Decision Record — ឯកសារកត់ត្រា "យើងបានជ្រើសអ្វី និងហេតុអ្វី" ដើម្បីកុំឱ្យអ្នកក្រោយសួរឡើងវិញ |
| Epic / Sprint / Task | ការងារធំ → វដ្តការងារ ១~២ សប្តាហ៍ → ការងារតូចជាក់លាក់ |
| DAG | Directed Acyclic Graph — ក្រាហ្វិកបង្ហាញថា Task ណាត្រូវរង់ចាំ Task ណា និង Task ណាអាចធ្វើស្របគ្នា |
| STRIDE | ក្របខណ្ឌវិភាគគំរាមកំហែង ៦ ប្រភេទ (សូមមើល §3.5) |
| ផ្ទៃវាយប្រហារ (Attack Surface) | គ្រប់ចំណុចដែលអ្នកវាយប្រហារអាចចូលដល់ប្រព័ន្ធ |
| Parity Test | ការសាកល្បងផ្ទៀងផ្ទាត់ថាប្រព័ន្ធថ្មីឱ្យលទ្ធផល **ដូចគ្នាបេះបិទ** នឹងប្រព័ន្ធចាស់ (ប្រើពេលធ្វើ migration) |
| Coverage | ភាគរយនៃកូដដែលត្រូវបានសាកល្បងគ្របដណ្តប់ |
| SLA | Service Level Agreement — កម្រិតសេវាកម្មដែលបានសន្យា |
| G2 Gate | ច្រកអនុម័តទី២ (រចនា) — ត្រូវឆ្លងទើបចាប់ផ្តើមសរសេរកូដបាន |
| CVSS | ប្រព័ន្ធពិន្ទុវាស់ភាពធ្ងន់ធ្ងរនៃចន្លោះប្រហោងសុវត្ថិភាព (០~១០) |

**លទ្ធផលចុងក្រោយ:** ឯកសារ ៦ ច្បាប់ (ផែនការអភិវឌ្ឍន៍ · ផែនការសាកល្បង · ស្ថាបត្យកម្ម · គំរូគំរាមកំហែង · ADR-001 · បញ្ជីហានិភ័យ) ដែលត្រូវឆ្លងច្រក **G2**។

## 2. ការសម្រេចចិត្តលើ Tech Stack — ADR-001

កាតព្វកិច្ចប្រៀបធៀបបេក្ខភាព ≥ ២ ជម្រើស។ វាយតម្លៃបេក្ខភាពនីមួយៗតាមវិមាត្រខាងក្រោម។

| វិមាត្រ | ទម្ងន់ |
|------|-------|
| ជំនាញរបស់ក្រុម | 25% |
| ប្រព័ន្ធអេកូ / សហគមន៍ | 15% |
| អាជ្ញាបណ្ណ / ថ្លៃដើម | 15% |
| ដំណើរការ (ធៀបនឹង NFR ដែលទាមទារ) | 15% |
| សុវត្ថិភាព (ប្រវត្តិចន្លោះប្រហោង) | 15% |
| ប្រតិបត្តិការ / ការត្រួតពិនិត្យ | 15% |

> **មូលដ្ឋាន**: វិមាត្រ ៦ និងទម្ងន់ខាងលើ ព្រមទាំងច្បាប់ "គម្លាតជាមួយជម្រើសទី២ < 10%" គឺ `[មូលដ្ឋាន:ការពិនិត្យឡើងវិញ sg-gw · អាចកែសម្រួលបាន]` (HARNESS-PROCESS-STANDARD §4.9)។ លទ្ធផល និងមូលដ្ឋាននៃការជ្រើសរើសត្រូវកត់ត្រាក្នុង ADR-001។
> **លទ្ធផល**: ជ្រើសជម្រើសដែលបានពិន្ទុខ្ពស់បំផុត ប៉ុន្តែបើ **គម្លាតជាមួយជម្រើសទី២ < ១០ %** នោះការអនុម័តដោយ PM ជាកាតព្វកិច្ច។

## 3. រចនាសម្ព័ន្ធស្តង់ដារនៃផែនការសាកល្បង

| ធាតុ | តម្លៃលំនាំដើម |
|------|-------|
| Coverage នៃការសាកល្បងឯកតា | បន្ទាត់ ≥ 80% / សាខា ≥ 70% |
| ការសាកល្បងសមាហរណកម្ម | បញ្ជាក់គោលនយោបាយ Mock សម្រាប់ភាពអាស្រ័យខាងក្រៅ |
| ការសាកល្បង E2E | សេណារីយ៉ូស្នូល TOP 5 |
| ការសាកល្បងសុវត្ថិភាព | ការផ្ទៀងផ្ទាត់ស្វ័យប្រវត្តិ OWASP Top 10 / ការស្កេនរកសម្ងាត់ / SAST |
| កម្រិតកំណត់នៃការវាយតម្លៃខ្លួនឯង ៧ វិមាត្រ | 90 / 100 |
| ការសាកល្បង Parity | (សម្រាប់តែ migration) សមមូលកម្រិត byte |
| ការសាកល្បងបន្ទុក | បន្ទុក ២ ដងនៃ SLA របស់ NFR-PERF |

> **មូលដ្ឋាន**: Coverage 80%/70% · E2E TOP5 · បន្ទុក ២ ដង គឺ `[មូលដ្ឋាន:ទម្លាប់ឧស្សាហកម្ម]` (អាចកែសម្រួលតាមគម្រោង); កម្រិតកំណត់ ៧ វិមាត្រ 90 គឺ `[មូលដ្ឋាន:ការពិនិត្យឡើងវិញ sg-gw · អាចកែសម្រួលបាន]`; OWASP/SAST/ការស្កេនរកសម្ងាត់ គឺ `[មូលដ្ឋាន:ស្តង់ដារខាងក្រៅ]`។ (§4.9)

## 3.5 ការធ្វើគំរូគំរាមកំហែង (STRIDE · ផ្ទៃវាយប្រហារ)

នៅដំណាក់កាលរចនា ត្រូវសរសេរ **គំរូគំរាមកំហែង** ១ ច្បាប់។ (ចាំបាច់មុន G2)

- **វិធីសាស្ត្រ**: ពិនិត្យ **ប្រភេទ STRIDE ទាំង ៦** (Spoofing ក្លែងបន្លំ / Tampering កែប្រែ / Repudiation បដិសេធ / Info Disclosure លេចធ្លាយព័ត៌មាន / DoS បដិសេធសេវា / EoP បង្កើនសិទ្ធិ) លើគ្រប់លំហូរទិន្នន័យដែលឆ្លងកាត់ព្រំដែនទុកចិត្ត + វិភាគ **ផ្ទៃវាយប្រហារ**។
- **ការតភ្ជាប់**: ផ្គូផ្គងវិធានការកាត់បន្ថយនៃគំរាមកំហែងនីមួយៗទៅ ADR សុវត្ថិភាព (ADR-004~008) / NFR-SEC — គំរាមកំហែង orphan ត្រូវមាន ០។
- **លក្ខខណ្ឌទប់ស្កាត់**: គំរាមកំហែងមិនទាន់ដោះស្រាយដែលមានកម្រិតស្មើ CVSS ≥ 7.0 ជាលក្ខខណ្ឌទប់ស្កាត់ G2/G3។
- **ការធ្វើបច្ចុប្បន្នភាព**: ត្រូវធ្វើបច្ចុប្បន្នភាពពេលមានការផ្លាស់ប្តូរស្ថាបត្យកម្ម · ឆានែលខាងក្រៅ · ការដំណើរការ PII (ការផ្លាស់ប្តូរត្រូវកត់ត្រាប្រវត្តិជា ADR)។
- **ផលិតផល**: `docs/design/threat-model.md` (គំរូ `templates/design/THREAT-MODEL.template.md`)

## 4. បញ្ជីហានិភ័យ (Risk Register)

កាតព្វកិច្ចកំណត់ ≥ ១០ ករណី។ `[មូលដ្ឋាន:ការពិនិត្យឡើងវិញ sg-gw · អាចកែសម្រួលបាន]` (ចំនួនអប្បបរមាជាសំណើផ្ទៃក្នុង — §4.9)។ ហានិភ័យនីមួយៗត្រូវប្រើទម្រង់ខាងក្រោម។

```
ID: RISK-NNN
ចំណងជើង: ...
វិស័យ: បច្ចេកទេស / កាលវិភាគ / ធនធានមនុស្ស / ខាងក្រៅ / សុវត្ថិភាព
ផលប៉ះពាល់: H / M / L
ប្រូបាប៊ីលីតេកើតឡើង: H / M / L
យុទ្ធសាស្ត្រឆ្លើយតប: ជៀសវាង / កាត់បន្ថយ / ផ្ទេរ / ទទួលយក
ផែនការឆ្លើយតប: ...
អ្នកទទួលបន្ទុក: ...
ពេលវេលាត្រួតពិនិត្យ: ...
```

## 9. គោលការណ៍សន្ទនា ១:១

- ពេលប្រៀបធៀបបេក្ខភាព ត្រូវ **ស្តាប់មតិ PM ជាមុនសិន រួចទើបវាយតម្លៃ**
- បើគម្លាតជាមួយជម្រើសទី២ < ១០ % ត្រូវ **ស្នើសុំការអនុម័តពី PM ជាដាច់ខាត**
- បើចង់បានតម្លៃផ្សេងពីកម្រិតកំណត់ ៧ វិមាត្រ 90 ត្រូវពិភាក្សា
- **លក្ខណៈវិនិច្ឆ័យសំណួរ**: ការសម្រេចស្មើគ្នានៃ stack (គម្លាតជម្រើសទី២ < 10%) និងការអនុម័តច្រក គឺជា **CQ3 (ត្រូវការសិទ្ធិមនុស្ស)**។ (លក្ខណៈវិនិច្ឆ័យ: HARNESS-PROCESS-STANDARD §4.8)
